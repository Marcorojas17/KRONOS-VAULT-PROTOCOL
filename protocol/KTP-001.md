## 1. Scope

KTP-001 defines a format for representing, sealing, and verifying
digital evidence. It specifies:

- The universal folio format.
- The canonical JSON serialization.
- The signature profile.
- The timestamping profile.
- The blockchain anchoring profile.
- The logical state model.
- A reproducible verification procedure.

It does **NOT** define:

- Evaluation methodology.
- Commercial certification.
- Legal validity of any claim.
- Identity of any party.

---

## 2. Conformance

The key words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and
**MAY** in this document are to be interpreted as described in
[RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and
[RFC 8174](https://www.rfc-editor.org/rfc/rfc8174).

An implementation is **KTP-001 compliant** at a given level if it
satisfies all **MUST** requirements of that level and of all lower
levels. Levels are defined in [`conformance/LEVELS.md`](conformance/LEVELS.md).

## 3. Terminology

| Term | Definition |
|------|------------|
| **Folio** | Identifier of a KTP evidence record |
| **Emisor** | Entity that generates a folio and signs credentials |
| **Credencial** | Signed JSON document containing a folio |
| **Verificador** | Any party verifying a credential |
| **Sellado** | RFC 3161 timestamp |
| **Anclaje** | Hash recorded on a public blockchain |
| **Estado** | Logical status of a folio: `0` (GREEN) or `1` (RED) |

The English-language forms (issuer, credential, verifier, timestamp,
anchor, state) MAY be used interchangeably in English text.

## 4. Universal folio

### 4.1. Structure

```
FVD-(MARCA)-NNNNN
```

| Part | Rule | Example |
|------|------|---------|
| Prefix | Literal `FVD` | `FVD` |
| Separator | Literal `-` | `-` |
| Brand | `[A-Z0-9]{2,20}` | `DEMO` |
| Separator | Literal `-` | `-` |
| Counter | `[0-9]{5,}` | `00001` |

### 4.2. Regular expression

```regex
^FVD-\([A-Z0-9]{2,20}\)-[0-9]{5,}$
```

### 4.3. Requirements

- An implementation MUST reject folios that do not match the regex.
- A folio MUST be unique within the issuer's namespace.
- The counter MUST increase monotonically within a brand.
- The folio MUST NOT contain lowercase letters, spaces, or accents.

### 4.4. Examples

Valid:

```
FVD-(DEMO)-00001
FVD-(TEXTILX)-00512
FVD-(PHARMA)-00001
```

Invalid:

```
FVD-demo-00001          (lowercase brand)
FVD-(DEMO)-1            (counter too short)
FVD-(A)-00001           (brand too short)
FVD-(DEMO)-00001-EXTRA  (trailing characters)
```

## 5. Canonical serialization

- Credentials MUST be serialized as JSON.
- The canonical form MUST follow [RFC 8785 (JCS)](https://www.rfc-editor.org/rfc/rfc8785).
- Whitespace MUST be stripped before hashing.
- Key order MUST follow JCS rules (lexicographic by UTF-16 code unit).
- Numbers MUST be serialized in ECMAScript number-to-string form.

---

## 6. Hash

### 6.1. Required algorithm

- SHA-256 (FIPS 180-4) MUST be used.
- The hash MUST be computed over the JCS-canonicalized bytes.
- The hex encoding MUST be lowercase, without separators.

### 6.2. Optional algorithms

- SHA-512 MAY be included for additional strength.
- SHA-1 and MD5 MUST NOT be used.

### 6.3. Example

```
sha256: 34c6e0182ce35b3bfb2488261746a689f5009a0a5260f128be06989b29d34dc
```

---

## 7. Signature

### 7.1. Required profile

- JWS detached (RFC 7797) over the canonical bytes.
- The signature MUST use Ed25519 (RFC 8032).

### 7.2. Allowed alternatives

- ECDSA P-256 MAY be used as an alternative.

### 7.3. Public key distribution

- The issuer MUST publish its public key.
- The key format SHOULD be JWK (RFC 7517) or a DID document.
- Key rotation SHOULD be documented.

### 7.4. Requirements

- A verifier MUST reject credentials whose signature does not
  validate against the issuer's published key.
- A verifier MUST reject credentials whose `kid` is unknown.

---

## 8. Timestamping

### 8.1. Required: double-seal

- Every credential MUST include at least two RFC 3161 timestamps.
- The two timestamps MUST be issued by independent TSAs.
- At least one TSA MUST be external to the issuer.

### 8.2. Format

Each seal MUST be represented as:

```json
{
  "type": "rfc3161",
  "authority": "Firmaprofesional SA",
  "timestamp": "2026-09-14T00:00:00Z",
  "url": "https://..."
}
```

### 8.3. Verification

- A verifier MUST verify the TSA certificate chain.
- A verifier MUST reject expired or revoked TSA certificates.
- A verifier MUST compare the sealed hash to the credential hash.

---

## 9. Blockchain anchoring

### 9.1. Supported chains

| Chain | Status |
|-------|--------|
| Ethereum | RECOMMENDED |
| Polygon | RECOMMENDED |
| OpenTimestamps (Bitcoin) | MAY be used |

### 9.2. Anchoring content

The anchor MUST include only:

- The SHA-256 of the credential.
- A reference to the folio.
- No personal data.

### 9.3. Format

```json
{
  "chain": "ethereum",
  "tx": "0x...",
  "timestamp": "2026-09-14T00:00:00Z"
}
```

### 9.4. Verification

- A verifier MUST confirm the transaction exists.
- A verifier MUST confirm the hash in the transaction matches the credential.

---

## 10. Logical states

### 10.1. Values

| Value | Name | Meaning |
|:-----:|------|---------|
| `0` | GREEN | Original, active |
| `1` | RED | Revoked |

### 10.2. Rules

- R1: A folio MUST start at state `0`.
- R2: The transition `0 → 1` is irreversible.
- R3: The transition `1 → 0` MUST NOT be allowed.
- R4: The revocation event MUST be timestamped immutably.
- R5: The current state MUST be publicly queryable.

---

## 11. Credential structure

A credential is a JSON object with the following required members.

```json
{
  "folio": "FVD-(DEMO)-00001",
  "version": "KTP-001/v0.1.0",
  "issued": "2026-09-14T00:00:00Z",
  "issuer": {
    "id": "did:example:issuer-01",
    "name": "Example Issuer"
  },
  "hashes": {
    "sha256": "34c6e018..."
  },
  "timestamps": [ ... ],
  "anchor": { ... },
  "state": 0
}
```

The authoritative shape is defined in
[`schemas/credential.schema.json`](schemas/credential.schema.json).

---

## 12. Verification procedure

A verifier MUST perform, in order:

1. Validate `folio` against the regex in §4.2.
2. Validate the credential against the JSON Schema.
3. Canonicalize per JCS.
4. Recompute SHA-256 and compare.
5. Verify the JWS signature.
6. Verify each timestamp against its TSA.
7. Verify the anchor on the referenced chain.
8. Query the current state.
9. Report the result as `GREEN`, `RED`, or `INVALID`.

A verifier MUST NOT rely on the issuer for any of these steps.

---

## 13. Error handling

- A verifier MUST reject credentials with missing required fields.
- A verifier MUST reject credentials whose signature fails.
- A verifier MUST reject credentials whose hash does not match.
- A verifier MUST report partial failures with a specific reason code.
